# LawCite TT YC-Style MVP Plan

**Date:** 2026-07-30

**Status:** Ready for implementation

**Build window:** 2–4 focused days

**Beta experiment:** 14 days

## Purpose

Launch the smallest credible version of LawCite that can answer one product
question with real Trinidad and Tobago legal professionals:

> Do lawyers and paralegals repeatedly use LawCite to find and verify statutory
> authority faster than their current process?

This is a learning release, not a reduced version of the complete legal
assistant vision. It deliberately excludes Chat, agents, a law graph, document
analysis, drafting, and case law.

## Product Promise

> Find and verify the applicable version of a Trinidad and Tobago statutory
> provision in under three minutes.

LawCite must help a professional move from a chapter, section, phrase, or legal
concept to:

1. The relevant statutory text
2. The correct version or historical cutoff
3. A copyable citation
4. The official source PDF

## Target User

Initial cohort:

- 5–10 Trinidad and Tobago lawyers and paralegals
- People who perform statutory research at least monthly
- A mixture of solo/small-firm practitioners and legal support professionals
- Users willing to complete at least three real research tasks during the beta
- Users willing to participate in a short opening and closing interview

Do not invite the general public during this experiment.

## Core Jobs

The MVP supports only these jobs:

1. Search for statutory provisions by words or legal concepts.
2. Narrow results by chapter and historical date.
3. Look up a known chapter and section.
4. Inspect available versions of a provision.
5. Validate and format a statutory citation.
6. Open the official source PDF.

## Included Scope

### Production security

Implement the existing private-beta authentication plan:

- Protect `https://law-cite-tt.gjo-ai.workers.dev` with Cloudflare Access.
- Use email one-time PIN authentication.
- Allow only explicitly invited email addresses.
- Proxy browser `/api/*` requests through the Worker.
- Verify Cloudflare Access JWTs in FastAPI.
- Reject direct unauthenticated API access.
- Add conservative API rate limiting.
- Provide a working logout action.

Reference:

`docs/superpowers/plans/2026-07-30-private-beta-authentication.md`

### Existing research product

Retain and verify:

- Grouped provision search
- Exact chapter/section lookup
- Chapter browsing
- Search-mode controls
- Historical date filtering
- Version selection
- Exact statutory excerpts
- Citation resolution
- Full and short citation copying
- Official PDF links
- Desktop and mobile layouts

### Beta readiness

Add only the minimum release affordances:

- A visible `Private beta` label
- A concise first-use explanation of Research and Cite
- A persistent `Send feedback` action
- A brief statement that LawCite is a research tool and users must verify
  authority against the official source
- A clear support contact
- Friendly authentication-expired and API-unavailable states

### Learning instrumentation

Record the minimum events needed to understand usage:

- Successful login
- Research search submitted
- Search result opened
- Historical date used
- Exact lookup submitted
- Citation resolved
- Citation copied
- Official PDF opened
- Feedback submitted

Use an opaque internal user identifier for analytics. Do not place email
addresses, search text, JWTs, or raw legal queries in third-party analytics.
Detailed research questions may be sensitive and should remain in controlled
server logs only when necessary for the beta study.

## Explicit Non-Goals

Do not add the following to this MVP:

- AI Chat
- Agents or agent frameworks
- Law-graph traversal
- Saved conversations or matters
- Long-term user memory
- Document uploads
- Case-law ingestion
- Research memo generation
- Drafting
- Billing or subscriptions
- Self-service registration
- Marketing website
- Custom domain
- Multi-role organization accounts

Hide the Chat navigation item for this release, or label it clearly as
unavailable. Do not present an empty feature as part of the beta value
proposition.

## Phase 0: Freeze the Experiment

**Duration:** Half a day

1. Confirm the product promise and target cohort.
2. Select the first 5–10 testers.
3. Record their role and current statutory research process outside the
   repository.
4. Prepare 10 representative evaluation tasks spanning:
   - Phrase/concept search
   - Exact chapter and section lookup
   - Historical-date research
   - Citation validation
   - Official source verification
5. Record the currently deployed Worker version and API image for rollback.
6. Run the existing frontend and backend test suites.

Exit condition:

- Scope is frozen.
- The initial tester list exists.
- Evaluation tasks and rollback versions are recorded.

## Phase 1: Secure the Beta

**Duration:** One focused day

Execute the private-beta authentication plan through production verification:

1. Add the same-origin Worker API proxy.
2. Remove the localStorage authentication stub.
3. Add FastAPI Access JWT verification.
4. Configure Cloudflare Access email OTP and the initial allowlist.
5. Protect or disable Worker preview deployments.
6. Add rate limiting.
7. Verify login, logout, session expiry, denied users, and direct API rejection.

Exit condition:

- An invited user can use the complete application.
- A non-invited user cannot load it.
- A direct unauthenticated Hostinger API request returns `401`.

## Phase 2: Prepare the Product Surface

**Duration:** Half to one day

1. Add the private-beta label and first-use explanation.
2. Hide or clearly disable Chat.
3. Add the research-tool/source-verification notice.
4. Add a persistent feedback action.
5. Add the support contact.
6. Add friendly `401`, `429`, API-unavailable, and empty-result states.
7. Add minimal event instrumentation.
8. Confirm that no analytics payload contains email, JWTs, or raw search text.

Exit condition:

- A first-time tester can understand what LawCite does without a live
  explanation.
- Every page has an obvious route to provide feedback.

## Phase 3: Production QA and Launch

**Duration:** Half to one day

### Automated checks

- Backend tests pass.
- Frontend tests pass.
- Production build succeeds.
- Authentication tests cover missing, malformed, expired, wrong-issuer, and
  wrong-audience tokens.
- Existing Research and Cite behavior remains covered.

### Browser checks

Verify desktop and mobile:

- Login by email PIN
- Research by phrase
- Chapter filtering
- Historical cutoff
- Exact lookup
- Version switching
- Citation validation
- Citation copy
- Official PDF opening
- Feedback action
- Session expiry
- Logout
- Rate-limit response

### Security checks

- Direct API access without authentication fails.
- Protected Worker preview URLs are not publicly usable.
- Access JWTs do not appear in logs or frontend storage.
- Invite emails are not committed to Git.
- CORS is narrowed to the required local-development behavior.

### Deployment order

1. Deploy and verify the Worker proxy.
2. Enable Access for the owner's email.
3. Confirm valid JWT forwarding.
4. Deploy mandatory FastAPI JWT verification.
5. Apply rate limiting.
6. Run production smoke tests.
7. Add the first tester only after the owner's complete workflow passes.

Exit condition:

- All automated, browser, and security checks pass.
- Production rollback identifiers are recorded.

## Phase 4: Two-Week Beta Experiment

### Day 0: Opening interview

Conduct a 20–30 minute conversation with each tester:

1. How do you currently find statutory authority?
2. What part of that process is slow or unreliable?
3. When did you last need an historical version?
4. How do you verify a citation before using it?
5. Ask the tester to complete one normal task without LawCite if practical.
6. Introduce LawCite only after understanding the existing process.

Do not lead with future Chat or agent features. Test the current statutory
research value.

### Days 1–3: First use

- Observe or accompany the tester's first LawCite task.
- Record where they hesitate, fail, or leave the product.
- Fix only release-blocking defects.
- Do not add major features during the experiment.

### Day 7: Midpoint check

Ask:

- Which real tasks did you attempt?
- Did LawCite produce the authority you expected?
- What did you still verify elsewhere?
- Where did it save or cost time?
- What prevented another use?

### Day 14: Closing interview

Ask:

1. Which task was most valuable?
2. Which result did you distrust, and why?
3. What tool would you use if LawCite disappeared tomorrow?
4. Would you continue using LawCite in its current form?
5. Would you pay for it? If so, which workflow justifies payment?
6. What is the next adjacent job: related laws, cases, saved matters, Chat, or
   drafting?

Avoid asking only whether they "like" the product. Ask about observed behavior,
replacement behavior, and willingness to continue.

## Metrics

### Activation

A tester is activated after completing all of:

- Successful login
- One research search or exact lookup
- Opening a result
- Opening an official source or copying a citation

Target:

- At least 5 activated testers

### Real usage

Targets over 14 days:

- At least 20 genuine research sessions across the cohort
- At least 3 activated testers return on a different day without prompting
- At least 10 official-source opens
- At least 10 successful citation or provision verifications

Exclude founder tests, automated checks, and demonstration sessions from these
counts.

### Task success

For the 10 prepared evaluation tasks:

- At least 8 can be completed without founder intervention.
- The correct source and version must be reachable.
- No displayed citation may point to a different provision.
- No historical result may be presented as current without a visible date or
  version label.

### Qualitative pull

The MVP shows meaningful pull when:

- At least 3 testers explicitly request continued access, introduce a
  colleague, or express credible willingness to pay.
- Testers can name a recurring workflow where LawCite is better than their
  current method.
- At least one adjacent request repeats across multiple testers.

## Decision Rules

### Proceed to the a16z-style workflow MVP

Proceed when:

- The security and source-integrity gates pass.
- At least 5 testers activate.
- At least 3 return independently.
- At least 3 demonstrate credible product pull.
- Feedback reveals a repeated adjacent workflow suitable for a narrow matter
  workspace or research agent.

Build the next MVP around the repeated workflow, not around the most impressive
technical feature.

### Iterate the existing research MVP

Continue improving Research and Cite when:

- Users value the problem but fail because of search relevance, metadata,
  historical labeling, or navigation.
- Users repeatedly ask for a small improvement that blocks routine use.

Run another short experiment after fixing the dominant failure.

### Reconsider the wedge

Reconsider the statutory-research wedge when:

- Testers rarely face the problem.
- They do not return despite successful tasks.
- They will not replace any part of their current workflow.
- The dominant need is consistently case law or document analysis rather than
  legislation.

Do not solve lack of demand by adding a broad Chat interface.

## Risks and Controls

### Incorrect or mismatched metadata

Control:

- Complete the 10-task evaluation.
- Preserve exact source and version labels.
- Keep the official PDF one click away.
- Record and prioritize any chapter/version mismatch.

### Beta users mistake LawCite for legal advice

Control:

- Position it as a professional research tool.
- Require source verification.
- Avoid client-facing claims and automated legal conclusions.

### Authentication blocks legitimate testers

Control:

- Start with the owner.
- Test email delivery and logout.
- Maintain a non-public support channel.
- Preserve the previous Worker and backend versions.

### Scope expands into the paralegal vision

Control:

- Treat all Chat, graph, matter, document, and drafting requests as research
  findings.
- Do not implement them during the 14-day experiment unless required to correct
  a security or source-integrity defect.

## Deliverables

### Product

- Secured production frontend and API
- Research and Cite beta surface
- Feedback path
- Minimal privacy-conscious instrumentation
- Tested rollback path

### Experiment

- Private tester roster outside Git
- Opening interview notes
- Usage summary
- Defect and trust-issue log
- Closing interview notes
- Fourteen-day decision memo

## Definition of Done

The YC-style MVP is complete when:

1. The secured product is live.
2. At least five target users have been invited.
3. Each invited user can complete the core workflow.
4. Two weeks of real usage and interviews have been captured.
5. A written decision chooses one of:
   - Build the narrow a16z-style workflow MVP
   - Iterate Research and Cite
   - Reconsider the statutory-research wedge

The output of this MVP is not merely software. It is evidence about whether
LawCite solves a recurring and valuable problem.
